# 旅行助手：本次改动与学习流程

本次回到 SmartVoyage，不继续改造 ResolveDesk。原课程 MCP 本来就是真实实现；问题在于固定地址、模型任意 SQL、预订工具返回固定成功文本，以及新离线演示没有经过实际网络服务。

| 部分 | 旧实现 / 前一轮 | 本次 |
| --- | --- | --- |
| 路由 | LLM 意图＋固定映射；此前新增能力目录 | 先读取配置内 AgentCard，过滤不可用 Agent，模型从可用目录规划多步骤任务 |
| 工具 | MCP 真实协议，查询接口接收模型 SQL | 实际 initialize、list_tools、Schema 校验、call_tool，工具接收城市/日期等业务参数 |
| 协作 | 领域查询；离线演示为替身返回 | A2A 网络分发，天气/票务可并行，票务结果回传后供预订 Agent 使用 |
| 预订 | 固定成功字符串 | 人工确认后在 SQLite 事务中保存模拟订单并扣样例库存；同请求 ID 重放 |
| 可见性 | 主要展示最终回复 | 页面显示可用服务、选择结果、依赖、协议和工具调用记录 |
| 部署 | 旧配置、多终端手工启动 | 独立依赖清单、服务启动器、Docker / Compose、GitHub CI |

## 一次复合请求怎么走

1. `intelligence/runtime.py` 选择规则或 LLM 模型，配置真实 A2A transport；旧完全离线模式仍供回归测试使用。
2. `intelligence/registry.py` 读取可信地址上的 AgentCard，检查地址与能力 ID。不可用的能力不进入本轮模型目录。
3. `intelligence/router.py` 将 BM25 候选、完整可用目录、历史与日期交给模型，输出天气、票务、预订任务及依赖。
4. `intelligence/engine.py` 按依赖执行；独立读取最多并发 2 路。预订生成待确认任务。
5. `intelligence/transport.py` 经 HTTP 发送 A2A Task，结构化传递上游结果。
6. `services/domain_agent.py` 连接 MCP，读取工具 Schema，按领域允许列表选择工具。LLM 模式提取参数；规则模式只支持有限演示表达。两种模式都真实走 MCP。
7. `services/mcp_tools.py` 调用参数化查询、天气适配或订单业务。工具不再直接返回固定成功文本。
8. 用户确认后，OrderAgent 根据用户数量和明确票号或唯一上游候选调用写工具。`services/data.py` 原子提交订单与库存变化。

查询 Agent 不能选择预订工具。上游查无数据会要求补充输入，依赖任务不会继续执行。没有配置模型时，规则演示不能宣传成 LLM 自动理解。

## 数据与协议边界

便携样例含三条虚构票务记录，固定日期为 2026-10-01，编号以 DEMO 开头。原 MySQL 数据未迁移；旧课程服务仍在本地，但不属于新默认发布链路。Open-Meteo 是可选真实天气适配，不代表票务也是实时。

模型可以选择已配置且在线的 Agent；未实现任意服务自动注册、动态加载未知代码、多轮自主重规划或跨进程审批恢复。订单去重键由 A2A Task ID 注入，保障同 Task 重放不重复扣库存；新 Task ID 不自动视为同一业务请求。

## 建议实验

- 输入示例复合问题，查看天气和票务是独立任务、预订依赖票务。
- 只启动部分 Agent，观察发现结果和能力目录变化。
- 查询样例外日期，观察 no_data 转为 input_required，预订依赖被阻断。
- 阅读 `tests/test_network.py`，解释 32 次同请求为何只扣一次库存、插入订单失败为何回滚。
- 配置自己的 LLM 后再测不同表达、缺参数和多个候选票；规则测试不能替代模型质量评估。
